## Security and reliability coverage

Local tests cover prompt injection/refusal, forged citations/property IDs, unavailable inventory,
provider exceptions, scoped retrieval, session/origin validation, PII handling, slot conflicts,
appointment contact/reference checks, explicit confirmation, declining a voice action, idempotency,
outbox retries and retained partial provider receipts. These finite cases do not establish universal
prompt-injection resistance or an independent penetration-test certification.

The active UrduLish route is Deepgram streaming STT, the structured OpenAI agent, and configured
Fish Audio (`s2.1-pro-free`) speech. The hybrid adapter now sends Deepgram `Finalize` at the browser
VAD boundary so the provider flushes the utterance while the conversation WebSocket remains open;
it sends `KeepAlive` during pauses and `CloseStream` only when the input session ends. Deepgram
documents `Finalize` as flushing the WebSocket stream and lists it separately from `CloseStream`,
which closes the connection ([Live Audio API](https://developers.deepgram.com/reference/speech-to-text/listen-streaming),
[Close Stream](https://developers.deepgram.com/docs/close-stream)). A regression test exercised
two browser turns through one STT stream. The live 2026-09-28 loop returned final transcripts,
agent replies and final audio on 3/3 synthetic turns without reopening the session. Final
transcripts arrived 862.8–1,339.8 ms after speech; substantive answer audio began at 1,375.7,
2,078.5 and 1,842.4 ms, so 2/3 met the two-second goal. Acknowledgements began around 430 ms and
are reported separately. The rent follow-up retained Karachi and rent intent; its raw transcript
rendered DHA as `T Ah Ah min`, which a deterministic parser regression now maps to the DHA area.
This does not correct ASR output or establish UrduLish human accuracy, p95, or physical
playback. Earlier close-per-turn timeout and multilingual-route experiments remain historical
evidence, not current behavior.

OpenAI Realtime transcription and optional Realtime TTS are unavailable for the configured account:
the handshake returned `insufficient_quota.credit_balance_exhausted`, and no caller audio was sent
through that route. The current `/readyz` reports the hybrid path available and OpenAI Realtime
voice unavailable.
The paid Fish Audio `s2.1-pro` route also returned an insufficient-credit response; its free model
has only limited synthetic evidence. ElevenLabs is unconfigured. Historical provider-only TTS
probes and earlier persistent-stream Finalize runs are retained above as dated evidence; the current
implementation uses Finalize with endpointing retained and adds a five-second KeepAlive. Earlier
experiments found no material gain from splitting TTS clauses
and no reliable UrduLish STT model improvement. They do not establish a two-second ceiling.

The 425 ms browser VAD preserves a 400 ms thinking pause in the 80 ms-frame regression. The current
Deepgram endpoint is configured at 300 ms; explicit hybrid turns are still finalized by browser VAD.
Prior disabling-endpointing experiments yielded interim Urdu but no final transcript before the
deadline, so that setting remains enabled. The 80 ms PCM prebuffer, bounded playback queue, stale
response rejection and explicit playback-drain state are regression-tested; browser-device audibility
still requires a human microphone check.

On 2026-09-29, three fresh three-turn synthetic hybrid WebSocket runs produced inconsistent
provider timing: the first run had a 5,772.7 ms final transcript on turn one (the other turns were
642.2 and 781.2 ms); the second run completed all turns in 626.2–849.9 ms; a third run against an
isolated API using the commit-before-acknowledgement code change had two finals at 1,359.8 and
1,998.8 ms, then no final on turn three before the configured deadline. Substantive answer audio
was under two seconds on 1/3, 3/3, and 0/3 turns respectively. The change sends the STT commit
before outbound acknowledgement playback, allowing the two paths to overlap; these samples do not
show a reliable latency improvement. All three runs returned some audio, but the third run's final
audio was the configured transcription-recovery prompt, not a contextual property answer. See
`live-voice-continuation-2026-09-29.json`,
`live-voice-continuation-repeat-2026-09-29.json`, and
`live-voice-commit-first-2026-09-29.json`. This synthetic sample is not a p95, native-speaker
quality score, or physical-microphone acceptance.

A subsequent live hybrid run on the restarted localhost server returned final transcripts and
contextual replies on 3/3 turns, but substantive answer audio took 2,540.7–2,777.5 ms, so the
two-second target still failed. A prior turn trace showed 4,688 ms in `grounded_resolution` with an
`llm:failures` event. A direct configured `gpt-4o-mini` request took 8,964.6 ms to fail despite the
1,500 ms SDK timeout. The provider now has a serialized single-worker call with a caller-side
wall-clock deadline and cooldown; a follow-up direct request returned `LLMDecisionError` to its
caller in 1,501.6 ms. The latest voice run did not exercise the slow model failure path, so the
deadline fix is covered by provider tests and the direct probe, not a claimed live voice comparison.
See `live-voice-llm-wall-deadline-2026-09-29.json` and
`openai-decision-wall-deadline-2026-09-29.json`.

Additional voice pipeline regressions cover legacy provider signatures, bounded current/next
clause prefetch, full-queue cancellation, provider cleanup and error recovery.

One dependency pending-deprecation warning remains in LangGraph's JSON-plus serializer. Voice playback uses an 80 ms PCM prebuffer, waits for playback drain before returning to listening,
bounds queued audio, rejects late decoded chunks after interruption, and reports decode/autoplay
errors in the UI. Audio input sends a bounded 300 ms lead-in and gates silence for OpenAI manual
transcription; recognition partials are surfaced as they arrive. Responses carry IDs so interrupted
turns cannot play stale audio. Browser capture uses AudioWorklet; the deprecated ScriptProcessorNode implementation has been removed.

The voice UI now shows separate session, microphone, transcription, agent reply, and audio
playback stages. After VAD ends a turn, it stays in a distinct “Transcribing” state until the
provider sends a final transcript; the transcript card remains visible during this wait. This
addresses the misleading listening indicator, not Deepgram's observed multi-second finalization.
It keeps the microphone in a starting state until an AudioWorklet frame arrives,
so a server-side listening state cannot masquerade as active browser capture. The troubleshooting
stepper stays collapsed during normal calls and opens on failure with its stage-specific retry action.
It waits for authentication before marking the session connected, distinguishes
microphone permission/device failures from later pipeline failures, warns when the input is silent,
and offers a retry appropriate to the failing stage. During a conversation it hides duplicate orbital
shortcuts and reports turn-end-detection-to-browser-playback timing separately from server-side
agent-decision time. A headless Chrome run completed one generated Urdu speech turn through the fake
microphone, live local API, transcript, agent response, and voice-output stage in 18.0 seconds; the
browser showed the reply and replay control. A separate permission-denial check confirmed the
microphone failure is visible instead of leaving the headline on “Listening.” These are
synthetic-browser checks, not human microphone or listening acceptance. When readiness fails, the page now explains that voice is unavailable,
shows provider blockers and any alternate ready route in a disclosure, and offers readiness retry,
language settings, and text-chat focus actions. Runtime-readiness payload validation and those
failure states are covered by frontend unit checks; the new error panel has not been separately
audited in a real browser viewport.
